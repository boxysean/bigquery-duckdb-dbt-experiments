# Challenges: what was hit building project 2, and how each was resolved

Everything here was **hit and measured** on 2026-10-07 (Trino 483, Spark 4.0.1, Iceberg
1.10.0, dbt-core 1.11.11, dbt-trino 1.10.2), not predicted. Each entry gives the symptom,
the cause, the resolution, and what it costs from now on. "Ongoing" marks costs that
recur whenever a model is added or changed. Those are what matter for the
build-vs-maintain comparison with project 1.

## 1. Tooling and platform

### 1.1 No dbt v2 adapter for Trino
- **Symptom**: dbt v2 (Fusion, dbt-oss 2.0.5), which project 1 uses, has no Trino
  adapter at all.
- **Resolution**: project 2 is dbt v1 (dbt-core). The model SQL and YAML written for dbt
  v2 ran unchanged on dbt v1: the shared tree parsed and built with zero edits
  attributable to the dbt version.
- **Ongoing**: the two projects sit on two dbt major versions with different features,
  CLIs and release cadences. Project-level config is not shared: project 1's
  `+static_analysis: strict` is a dbt v2 setting, so project 2's `dbt_project.yml`
  leaves it out, and `config-version: 2` is required on dbt v1 only.

### 1.2 dbt v1 needs a BigQuery credential just to compile
- **Symptom**: `dbt compile --target bigquery` fails with `Failed to authenticate with
  supplied credentials` when no credential exists. dbt v2 compiled BigQuery with none
  (project 1's CI relies on that).
- **Cause**: dbt-bigquery builds credentials when it opens a connection, even if no query
  ever runs.
- **Resolution**: `--no-populate-cache --no-introspect` plus a **throwaway,
  structurally valid service-account key** generated by `scripts/check_portability.py`.
  It is never sent anywhere, because no query runs. CI compiles BigQuery on every PR with
  no secret.
- **Ongoing**: a workaround to keep alive, with a regression risk if a future dbt-bigquery
  authenticates eagerly.

### 1.3 Adapter-specific configs are "custom keys" on the other target
- **Symptom**: `CustomKeyInConfigDeprecation` for `+on_table_exists` and `+properties` when
  compiling for BigQuery.
- **Cause**: in dbt v1, `dbt_project.yml` configs are not per-target, and a config one
  adapter defines is unknown to the other.
- **Resolution**: accepted, documented in `dbt_project.yml`. It is a warning, not an error.
- **Ongoing**: every Trino-only table setting produces BigQuery-side noise. A dbt-trino
  model-level `properties` dict replaces the project-level one, so a model that sets
  partitioning must repeat the project-wide property (see 3.2 and
  `macros/polyglot/physical.sql`).

### 1.4 Container images and downloads
- MinIO stopped publishing community images in 2025, so the stack uses **SeaweedFS** for
  S3.
- Docker Hub rate-limited pulls (`429 Too Many Requests`), so images are pulled from
  `mirror.gcr.io` by default (`IMAGE_REGISTRY` overrides it).
- Maven Central rate-limited the Iceberg jar download (`429`), so
  `scripts/fetch_spark_jars.sh` falls back to Google's Maven mirror and checks the sha256
  either way.
- The Iceberg REST fixture image runs as a non-root user that cannot write a fresh
  volume, so its compose service runs as root. Its default catalog schema (V0) cannot
  store **views**, so the stack sets `CATALOG_JDBC_SCHEMA__VERSION=V1`.
- **Ongoing**: about 6 GB of images, and a 4-container stack to keep healthy. Project 1's
  DuckDB leg is a single file.

## 2. Trino and BigQuery SQL dialects (the macro seam)

All resolved inside `macros/polyglot/`. The model SQL is byte-identical to project 1's.

| # | Difference | Resolution |
|---|---|---|
| 2.1 | **No named struct constructor on Trino.** `ROW(1, 'x')` has anonymous fields; naming them needs `cast(row(..) as row(a bigint, ..))`, which needs every field's **type** | `struct_literal` takes `[name, expr, type]`. This was the **only change to shared model code**: `mart_polyglot_types` now passes the types. Project 1's macro accepts and ignores them, so its render is unchanged (verified on BigQuery) |
| 2.2 | **No `to_json` on Trino**, and **Iceberg has no JSON type** | `to_json_value()` macro (added to both projects). On Trino it is `json_format(cast(x as json))`, stored as **varchar**. Column type: `json` on BigQuery, `varchar` on Trino/Spark |
| 2.3 | **No star modifier on Trino** (`* EXCEPT` / `* EXCLUDE` / `* REPLACE`) | `trino__except_columns` is a compiler error with an explanation. No model uses it; project 2's showcase analysis lists columns by hand |
| 2.4 | Trino's bare `timestamp` is `timestamp(3)`, **milliseconds** | `timestamp_type()` = `timestamp(6)`; self-check proves microseconds survive |
| 2.5 | **No microsecond unit in Trino `date_diff`**, and timestamp subtraction gives a millisecond `INTERVAL` | `seconds_between` = `round(to_unixtime(e) - to_unixtime(s), 6)`; self-check proves 1 µs and a 4-year span |
| 2.6 | `md5` takes varbinary and `to_hex` is **uppercase** on Trino | `lower(to_hex(md5(to_utf8(concat_ws('||', ..)))))`. The self-check proves the **same MD5 as DuckDB and BigQuery** (`df6729…`) |
| 2.7 | `SAFE_DIVIDE` missing; Trino double ÷ 0 gives **Infinity/NaN, not an error** | `nullif` on the divisor |
| 2.8 | `date_format` uses MySQL-style codes (`%i` = minutes, `%M` = month name), not strftime | Documented in the macro; the codes the project uses (`%Y %m %d %j`) agree. Spark's `date_format` is different again (Java patterns) |
| 2.9 | `unnest ... as x` binds the table on Trino | `unnest_alias` renders `x__unnest(x)`, as on DuckDB |
| 2.10 | `sequence` over dates only takes DAY or MONTH intervals | Weeks become 7n days, quarters 3n months, years 12n months; a month-end start does not drift (self-check) |
| 2.11 | Regex: Trino uses Java regex by default, BigQuery RE2 | Same results on ordinary patterns; look-around and backreferences would diverge. Documented |
| 2.12 | Geography: `SphericalGeography` cannot be stored in Iceberg, and Spark has no geography type | Stored as WKT varchar; `geography_type()` = varchar |
| 2.13 | Rendering: Trino casts a double to text in scientific notation (`2.5E-1`) and quotes row field names in `typeof` | Only affects self-check expected strings |

**Ongoing**: the same discipline as project 1. A model author must use the macros, and
the portability guardrail fails the PR otherwise. Gaps 2.1 and 2.3 are **stricter than
project 1** (Trino needs types where BigQuery and DuckDB infer them, and has no star
modifier), so a little more is asked of every model author.

## 3. Trino on Iceberg (the lakehouse)

### 3.1 Daily partitions fail, and would be wrong anyway
- **Symptom**: `ICEBERG_TOO_MANY_OPEN_PARTITIONS: Exceeded limit of 100 open writers for
  partitions: 177` building `fct_inventory_items` with BigQuery's `day(created_at)`
  layout.
- **Resolution**: `month(created_at)` plus `sorted_by product_id` on Iceberg. Raising
  `iceberg.max-partitions-per-writer` would make the build pass, but every day would
  become its own tiny Parquet file. On a lakehouse, per-file overhead is the cost.
- **Ongoing**: physical layout is a per-engine design decision, not a translation.

### 3.2 `CREATE OR REPLACE` vs build-then-rename
- dbt-trino's default `on_table_exists: rename` drops and re-creates the table, which gives
  it a **new Iceberg identity and history** every run. A Spark reader holding the table
  can see it vanish.
- **Resolution**: `+on_table_exists: replace` (`CREATE OR REPLACE TABLE`) on marts: same
  table, new snapshot.

## 4. Trino ↔ Spark interoperability

### 4.1 Spark cannot read 5 of 12 Trino-written tables (Parquet v2 encodings)
- **Symptom**: `UnsupportedOperationException: Cannot support vectorized reads for column
  [email] ... with encoding DELTA_LENGTH_BYTE_ARRAY` on `dim_users`, `dim_products`,
  `dim_distribution_centers`, `fct_inventory_items` and `mart_cohort_retention`.
- **Cause**: Trino's Parquet writer uses Parquet v2 encodings for text, and Iceberg's
  vectorized Spark reader supports only v1 encodings. This is a known issue
  ([apache/iceberg#7162](https://github.com/apache/iceberg/issues/7162)); Athena, which
  is built on Trino, hits it too.
- **Resolution**: dbt writes every table with
  `extra_properties = map(array['read.parquet.vectorization.enabled'], array['false'])`.
  The key has to be allow-listed in the Trino catalog
  (`iceberg.allowed-extra-properties`). After that, 12 of 12 tables are read identically.
- **Ongoing**: Spark reads these tables with its slower row-based Parquet reader (cost
  not measured). A model that sets its own `properties` must repeat the key. A **new
  table that forgets it fails only when Spark reads it**, and the interop gate is what
  catches that in CI.

### 4.2 No dbt-built view is readable by Spark
- **Symptom**: `AnalysisException: Invalid view name: lake.analytics_dev.stg_thelook__orders`
  for all 18 views.
- **Cause**: an Iceberg view stores its SQL in one dialect. dbt-trino writes
  `"lake"."thelook_ecommerce"."orders"`, and Spark reads double-quoted text as a string,
  not an identifier.
- **Measured further**: a hand-written Trino view using a Trino-only function fails on
  Spark (`ROUTINE_NOT_FOUND: to_iso8601`). A view whose SQL happens to parse in both is
  **re-executed by Spark with Spark semantics**: `select 7/2` is `3` on Trino and `3.5` on
  Spark. Spark refused it only because the stored view schema said `integer`.
- **Resolution**: the rule "what Spark reads is a table". Marts are tables; staging and
  intermediate are Trino-internal views. That views are unreadable is the **safe**
  outcome: a readable cross-dialect view is the dangerous case.
- **Ongoing**: deciding a model's materialization now also means deciding who can read
  it. Project 1 has no equivalent concern.

### 4.3 Time zones
- Sources are instants (`timestamptz`). The models convert them to naive UTC
  `timestamp(6)` (`to_utc_timestamp`), which Spark reads as `TIMESTAMP_NTZ`. Spark's
  session time zone is pinned to UTC (`spark-defaults.conf`), and so is Trino's
  (`profiles.yml timezone: UTC`). The interop profile compares timestamps as epoch
  microseconds, and they match.
- **Ongoing**: three engines' time-zone settings must agree. A Spark session left on a
  local time zone would render the same instants differently, which is the risk the
  archived dbt v2 Spark project also documented.

## 5. What did *not* cause trouble

- The 168 data tests, including the custom singular tests, passed on Trino the first
  time.
- 29 of the 30 models needed **no** change at all; the 30th needed only typed struct
  fields.
- Decimal(38,9) money behaved: sums, division and rounding gave the same profile on
  Spark and Trino, and the sub-cent source digits survive.
